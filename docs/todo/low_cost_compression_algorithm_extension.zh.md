# 压缩算法扩展的剩余设计问题

> 类型：研究者扩展体验 TODO
> 状态：注册、开发运行与完整示例已实现；以下问题按实际扩展需求推进。
> 原记录日期：2026-08-12；范围更新：2026-09-10。

## 当前入口

新增方法以[开发指南](../guides/2_dev_compression_method.zh.md)和
[图像、音频、视频完整示例](../../examples/compression_extensions/README.md)为准。

- 更换现有数学步骤时，使用 `operation.rules`。
- 复用已有计划、预算和配置规则时，`register_method` 接受新方法名、复用的 Binding
  和 strategy 工厂；FirstK 与 LTBM 示例共用此入口，省去改名插件类和重复声明。
- 改变计划或执行接口时，显式提供 Algorithm 和 strategy/executor 工厂；两种写法
  都生成同一套普通合同，不复制支持证据。
- 显式选择的研究方法可以开发运行；正式支持状态仍由相应验证证据决定。

注册不能建立执行兼容性。方法仍需遵守所选执行器实际使用的数量、索引、请求状态及
重放接口。这些接口和可运行教程已有独立文档，不再作为本 TODO 的待建内容。

## 剩余问题与启动条件

### 1. 已有机制的选择与兼容性说明

目前作者明确选择 `reuse_bindings`，框架尚未根据一份通用 `requirements` 自动匹配
执行能力。是否需要这种匹配，应由实际接入成本决定，不把它作为新方法的前置条件。

当另一方法复用同一执行机制时，若仍需重复声明相同能力，或难以判断缺少哪种输入、
位置或生命周期支持，先定位重复事实和错误反馈，再决定是改进指南、局部校验还是
共享声明。只有实际需要匹配的能力稳定后，才讨论自动匹配；不预建任意能力系统。

### 2. 数量计划与运行时结果的一致性

当前已有精确预算和数据依赖预计算路径，但尚无覆盖各执行族的统一数量合同。
新增方法若出现重复预算逻辑、计划与实际数量不一致，或现有机制无法表达的运行时
数量变化，按[数量合同 TODO](token_compression_cardinality_execution_model.zh.md)
处理；本文件不再维护另一份合同定义或迁移路线图。

### 3. 现有执行器无法承接的方法

新的物理位置、基座、模态布局或状态生命周期可能需要新增 Binding/provider 或扩展
执行器。先分清算法差异与共享执行职责，再用另一算法验证复用，不要求所有方法改为
同一个类、返回类型或注册语法。

动态与混合 Operation 执行仍由
[Operation TODO](operation_compression_execution_model.zh.md)记录；跨阶段数量与
位置语义分别以数量合同 TODO 和
[位置语义问题](token_position_semantics_open_questions.zh.md)为准。
没有具体方法或失败案例时，不为这些方向补空接口。

## 完成边界

每次扩展改进围绕实际阻碍验收，不以实现全部设想的统一接口为结束条件：

- 复用既有能力的新方法不因方法身份而修改共享 runtime、Controller、lmms-eval 或
  ms-swift；算法参数和数学决定没有多份需要同步的定义。
- 共享机制确实处理布局、位置、标签、缓存及安装卸载；方法保留其数学和必要状态。
  验证按所声称的训练、推理或恢复能力选择，不要求每个新方法跑全框架矩阵。
- 新机制与算法分别实现；新基座不复制算法 kernel，新模态明确表达真实布局差异。
- 开发运行继续经过配置和执行能力校验；一次成功运行不自动产生正式支持证据。
- 新增或改变的用户步骤回写开发指南与对应示例，本文件仅保留尚未解决的问题。

不恢复旧 Descriptor API，不增加任意目录自动发现、代码生成器或推测性的 target site
抽象，也不为了名称统一重写已经可复用的生命周期。
